## 先回答：这个项目现在有没有竞争力？

当前是一个可运行的本地论文 RAG 与证据核验应用，Skill 是其中的使用入口。完整性具备了，差异化证据还不足。已有混合检索、范围过滤、原文回填、有限审核循环、网页和 GEPA 离线试验；尚未证明这些设计比简单基线带来稳定、可泛化的收益。不能把“接上 GEPA”直接写成“实现持续自进化”。

面试价值应落在能解释、能对照、能复现的设计上，而非框架数量。建议下一阶段围绕“证据驱动的论文研究策略优化”展开：收集失败轨迹，区分召回、选证、回答和审核错误；只允许修改限定的提示词或检索参数；用训练材料提出候选、验证材料选择候选，再用保留论文检查；达标才升级策略版本，未达标保留基线。推广、回滚和持续运行闭环目前是补强方案，未实现。本次 GEPA 试验只完成很小规模的离线选择提示词优化，结果没有提升。

## 一、项目定位与技术选型

### Q001【P0】用一分钟介绍这个项目。

**参考回答：** 这是基于用户导入论文的调研与证据核验工具。用户指定论文和摘要/全文范围后，系统先规划查询，通过 BM25 与 E5 混合召回，选择证据，生成回答，再做程序校验和模型审核。报告保留原文、PDF 页码与提取文本字符位置。我希望解决的是“答案能否回查、材料不足时能否停止”，当前还在小规模演示阶段。

**追问准备：** 当场跑 QASPER 数量与 GPU 问题：前者有摘要证据，后者只能说摘要无法确认。依据：[真实报告](../output/live_qasper/report.json)、[主流程](../paper_research/workflow.py#L35)。

### Q002【P0】为什么做论文场景，和普通知识库问答有什么区别？

**参考回答：** 论文场景更强调结论对应哪项实验、比较条件是否一致，以及某个结论能否从限定材料中确认。实现上我增加了摘要范围、跨论文来源覆盖和原文位置回填。这个场景选择是工程练习与求职定位，目前没有用户调研或真实业务数据证明需求规模，不能虚构节约科研时间的百分比。

**追问准备：** 为什么不叫 Deep Research？当前没有自主全网检索与连续文献发现，应描述为本地论文研究助手。依据：[项目范围](../README.md)。

### Q003【P0】这不就是套壳 RAG 吗？创新在哪里？

**参考回答：** 基础技术没有原创性，目前也没有声称提出新算法。可讨论的工程设计是范围前置过滤、模型只引用证据编号、程序回填原文、有限补查，以及失败回归。竞争力取决于这些设计有没有经过对照验证。目前实验规模很小，因此我会把它定位为有完整验证链的应用原型，而不是成熟研究贡献。

**追问准备：** 提出可证伪的下一步：去掉证据回填或审核，比较引用真实性、语义支持和误拒答，而不是只展示成功截图。依据：[引用实现](../paper_research/grounding.py#L37)、[测试](../tests/test_grounding.py)。

### Q004【P1】为什么不直接用一个超长 Prompt？

**参考回答：** 一次性输入可以作为基线，短论文可能很合适。分阶段流程便于定位召回、选择、生成还是审核失败，也能控制材料范围和单步输出。代价是额外调用、延迟和错误传播，不能只凭结构复杂就说更好。下一步应在同一批任务上比较全文直输、简单 RAG 和当前流程的质量与成本。

**追问准备：** 长上下文不必然完全利用材料，但旧论文结论也不代表所有新模型都一样。相关实验依据：[Lost in the Middle](https://arxiv.org/abs/2307.03172)；当前实现依据：[workflow](../paper_research/workflow.py)。

### Q005【P0】为什么选 LangGraph？不用它行不行？

**参考回答：** 可以用普通函数和循环实现。目前选 LangGraph 是为了把状态、阶段和审核后的分支显式表示，便于查看轨迹和测试退出条件。它没有自动提高答案质量，持久化、并发和恢复也必须实际配置。本项目主要使用 StateGraph、节点、普通边和条件边，没有把框架所有能力都接入。

**追问准备：** 画出 verify 后回到 retrieve 或进入 finish 的条件。依据：[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[实际建图](../paper_research/workflow.py#L165)。

### Q006【P1】LangChain、LangGraph、Deep Agents 在本项目分别用了什么？

**参考回答：** 应用用 LangGraph 管流程，用 HTTPX 直接调用模型兼容接口；没有另外接 Deep Agents，也没有通过 LangChain 模型适配层调用 Qwen。安装依赖里出现某个包，不代表应用使用了它的全部能力。早期方案和最终实现不完全相同，应按最终代码解释，不能把规划里的技术栈全部写进简历。

**追问准备：** 为什么没再套一层？当前工具和流程有限，增加框架需要有明确收益。依据：[依赖与版本](../requirements.lock.txt)、[模型调用](../paper_research/model.py#L20)。

### Q007【P0】Skill 是整个系统吗？为什么里面要有代码？

**参考回答：** Skill 描述什么时候采用这套方法、先读哪些资料、调用哪些脚本以及如何输出。代码负责可重复、可检查的解析、检索和引用处理。宿主仍需理解问题与判断材料。这个 Skill 依赖外层 Python 包、索引和模型缓存，复制 SKILL.md 不会自动复制整个应用，更不能替代环境准备。

**追问准备：** packet 模式返回材料，交给宿主回答；agent 模式由独立 Qwen 流程处理。依据：[技能入口](../.agents/skills/paper-research/SKILL.md)、[工具流程](../.agents/skills/paper-research/references/local_workflow.md)。

### Q008【P1】Tool、MCP、A2A、Skill 怎么区分？

**参考回答：** 在这里，Tool 是有参数与结果的具体操作；Skill 是一套任务方法及配套资源；MCP 是连接应用与外部工具/数据的协议；A2A 处理不同 Agent 系统间的协作互通。当前项目没有实现 MCP server 或 A2A 服务，也不能把一个进程里多个模型角色叫成已落地的 A2A。

**追问准备：** 若以后要让独立文献搜索 Agent 与核验 Agent 交付任务，才评估 A2A 的必要性。依据：[MCP 官方介绍](https://modelcontextprotocol.io/docs/getting-started/intro)、[A2A 官方说明](https://a2a-protocol.org/latest/topics/what-is-a2a/)、[本地 Skill](../.agents/skills/paper-research/SKILL.md)。

### Q009【P0】为什么 RAG，而不是继续用 LoRA 微调？

**参考回答：** RAG 在推理时取外部材料，适合论文不断更新和答案需要来源的位置；LoRA 训练低秩参数更新，适合学习行为或任务能力。两者可以组合，但微调不能自动提供可靠出处，RAG 也不能替代所有能力训练。本项目没有训练 Qwen，也没有训练 E5。

**追问准备：** 两个简历项目的区别：一个验证模型适配与部署，另一个验证检索、证据和服务流程。依据：[RAG 原论文](https://arxiv.org/abs/2005.11401)、[LoRA 原论文](https://arxiv.org/abs/2106.09685)。

### Q010【P0】你个人做了什么？有没有真实用户和上线结果？

**参考回答：** 这是 AI 协助完成的个人原型，目前是本地运行，没有真实上线用户或商业收益。我的面试准备应落实到亲自运行、解释并修改关键模块，例如调整 RRF 权重、加入不同论文的证据题、定位一次误拒答。尚未实际完成的个人工作不能按模板说成已经独立完成。

**追问准备：** 准备一段自己确实修改过的代码及修改前后记录；仅背技术名词经不起追问。依据：[交付说明](../README.md)、[已有验收](../output/acceptance.json)。

## 二、Agent 与 LangGraph

### Q011【P0】这个项目到底是 Agent 还是工作流？

**参考回答：** 更准确地说是包含模型决策节点的受控工作流。阶段和工具路径由程序规定，模型负责查询规划、证据选择、回答及审核，不能随意决定调用任意工具。这样的边界适合先验证论文证据任务，不应该包装成完全自主的通用研究 Agent。

**追问准备：** 决策自由度在哪？模型可以改变查询与选证，是否补查由固定条件路由。概念依据：[Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)；实现：[research](../paper_research/workflow.py#L35)。

### Q012【P1】State 保存哪些信息？

**参考回答：** State 包含原问题、范围、论文编号、模式、查询、轮次、证据包、报告、审核结果和反馈。节点返回部分字段更新。原始问题作为稳定锚点，防止模型规划后偏离用户问题；候选材料与回答分开，便于检查哪些材料真的进入生成。

**追问准备：** trace 和 drafts 当前是一次调用中的局部列表，未全部建成图状态通道，后续做 checkpoint 要重新审视。依据：[State](../paper_research/workflow.py#L12)、[状态语义](https://docs.langchain.com/oss/python/langgraph/graph-api)。

### Q013【P1】Node、Edge、Conditional Edge、Reducer 是什么？

**参考回答：** 节点执行阶段工作，普通边规定下一阶段，条件边根据状态选择后续路径，Reducer 规定多个更新如何合并同一状态字段。本项目没有自定义累加 Reducer，使用默认覆盖语义。若并行分支同时更新候选列表，必须显式设计合并与去重，不能假定列表自动追加。

**追问准备：** 未配置 Reducer 时返回新列表会覆盖旧列表。依据：[Reducer 文档](https://docs.langchain.com/oss/python/langgraph/graph-api#reducers)、[建图代码](../paper_research/workflow.py#L178)。

### Q014【P0】模型和代码各自负责什么？

**参考回答：** 模型负责语言理解与语义判断；代码负责允许材料、编号映射、引用位置、类型规则、轮次和调用上限。不能让模型自己决定它有没有权限读正文、自己填写引用页码，或仅靠一句“不要编造”约束可验证事实。语义支持仍需模型或人工判断，代码不能解决所有语言推理。

**追问准备：** 说出一个模型输出被程序拒绝的例子：引用未知 U 编号。依据：[canonicalize](../paper_research/grounding.py#L37)、[grounding 测试](../tests/test_grounding.py)。

### Q015【P1】你实现的是 ReAct 吗？Function Calling 呢？

**参考回答：** 当前不是标准的开放式 ReAct 工具循环，也未使用模型原生 tool_calls。程序直接调用固定工具，模型返回规划或选证的 JSON。ReAct 是推理与行动交替的一种模式；如果以后开放工具选择，还需要工具 schema、参数校验、权限、执行错误返回及退出条件。

**追问准备：** JSON 写了工具名不等于已经实现安全工具调用。依据：[ReAct 原论文](https://arxiv.org/abs/2210.03629)、[调用层](../paper_research/model.py#L60)。

### Q016【P0】第二轮到底改变了什么？反馈有没有用于检索？

**参考回答：** 第二轮增加最终召回数量，并改用原始问题作为语义查询；关键词查询仍沿用规划结果。上一轮反馈进入后续回答提示词，但没有被模型用于重新规划检索查询。因此当前是有限补查，还不是依据错误类型主动选择新工具或自适应改写的闭环。

**追问准备：** 这正是可增强处：把“缺少哪个证据”转成受控补查计划，再验证收益。依据：[retrieve](../paper_research/workflow.py#L68)、[draft](../paper_research/workflow.py#L127)。

### Q017【P0】怎样避免无限循环、费用失控和长时间卡住？

**参考回答：** 最多两轮、模型请求预算 8 次、输出 token 上限、HTTPX 超时和图递归限制共同约束。网络重试也消耗预算。当前没有独立的端到端强制截止时间，HTTPX 超时主要限制网络阶段等待，不能把它说成整个任务一定 60 秒结束；需要更强控制时增加截止时间和可取消执行。

**追问准备：** 第一轮正常 4 次调用，补查最多再 3 次，不含网络重试。依据：[workflow](../paper_research/workflow.py#L35)、[ModelClient](../paper_research/model.py#L20)、[HTTPX 超时语义](https://www.python-httpx.org/advanced/timeouts/)。

### Q018【P1】规划 JSON 错了、接口断了，分别怎么处理？

**参考回答：** 规划结构无效会回退原问题；选证结构无效会保留受限候选；回答或审核格式错误进入有限重试。接口鉴权、额度、网络基础设施错误不应变成“论文没有答案”，而应让任务失败并记录错误。语义不足和技术失败需要分开统计。

**追问准备：** 目前 HTTP 状态错误统一报失败，尚未按 429/5xx 做精细退避。依据：[错误边界测试](../tests/test_workflow.py)、[模型错误处理](../paper_research/model.py#L20)。

### Q019【P1】短期记忆、长期记忆在这个项目怎么做？

**参考回答：** 一次任务内的状态是短期上下文；SQLite 和文件保留任务与实验产物。系统没有实现跨对话提取、检索并应用用户偏好的长期记忆。保存历史记录不等于模型会在下一次任务自动使用它，也不等于个人化记忆已经完成。

**追问准备：** 若新增记忆，先定义内容、有效期、权限与纠错方法。概念依据：[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)；现状：[Store](../paper_research/storage.py#L10)。

### Q020【P1】多 Agent 是否一定比单 Agent 好？

**参考回答：** 不一定。分角色可能让职责清楚，也会增加延迟、成本和信息交接错误。当前主流程和审核只是相同模型服务的不同提示词角色，不能假定错误独立。应比较单次回答、程序检查、再加审核的消融结果，评估正确率、误拒答与调用成本，再决定是否保留额外角色。

**追问准备：** 没有做过这些完整消融，不应声称多 Agent 显著提升。依据：[review 节点](../paper_research/workflow.py#L146)、[相关测试](../tests/test_workflow.py)。

## 三、PDF、分块与索引

### Q021【P0】从 PDF 到可检索材料，完整过程是什么？

**参考回答：** 保存原 PDF、来源和校验和，逐页提取文字，识别摘要边界，再按页和区域切分，保存 raw_text 与清洗后的 text。检查 token 长度并继续细分超长片段，然后编码、归一化并保存索引。查询结果始终带论文、PDF 页码和原页字符区间。

**追问准备：** 这些是材料入库步骤，不是模型训练。依据：[document_chunks](../paper_research/indexing.py#L22)、[build_index](../paper_research/indexing.py#L82)。

### Q022【P0】为什么切分？为什么是 1000 字符、200 重叠？

**参考回答：** 分块让检索定位到局部证据，也控制编码与生成输入。当前 1000 字符、200 重叠是工程初始值，没有充分实验说明最优。过小容易丢条件，过大容易混入噪声；后续应在固定问题和原页证据标注下比较不同大小、重叠及按段落切分方案。

**追问准备：** 当前还做了 token 超长细分，最终不都是 1000 字符。依据：[分块参数](../paper_research/indexing.py#L22)、[fit_chunks](../paper_research/indexing.py#L53)。

### Q023【P0】字符数、token 数、向量维度有什么区别？

**参考回答：** 字符数是文本长度，token 数取决于 tokenizer 的切词，向量维度是编码器输出空间的大小。相同字符数在中英文、公式和特殊符号下可能对应不同 token 数。当前片段编码输入最多 512 tokens，输出 384 维；18000 候选字符是另一个粗略约束。

**追问准备：** 所有限制都要包含 query:/passage: 前缀和特殊 token。依据：[长度检查](../paper_research/embedding.py#L17)、[E5 模型卡](https://huggingface.co/intfloat/multilingual-e5-small)。

### Q024【P1】超过 E5 输入限制怎么办？为什么不静默截断？

**参考回答：** 建库时递归二分超长片段，保留适量重叠和原页偏移，直到每块满足输入限制。查询过长则报错，需要缩短或拆解。静默截断可能丢掉关键证据，却仍保留整个片段的元数据，使检索过程难解释；因此代码显式检查长度。

**追问准备：** 极端短文本仍超长会拒绝，避免死循环。依据：[fit_chunks](../paper_research/indexing.py#L53)、[Embedder.encode](../paper_research/embedding.py#L17)。

### Q025【P0】为什么同时保留 raw_text 和 text？

**参考回答：** text 用于清洗后的编码和关键词匹配，raw_text 用于引用及位置回查。清洗会改变空白、断行甚至字符数量，所以不能用清洗文本的偏移冒充原文位置。最终引文必须是对应 raw_text 的连续子串，字符范围再映射回原页。

**追问准备：** 当前原文位置指 PDF 提取文字中的位置，不是页面视觉坐标。依据：[canonicalize](../paper_research/grounding.py#L37)。

### Q026【P0】只读摘要怎样防止正文混进来？

**参考回答：** 建库时标记 abstract，查询时先过滤范围，再分别评分与融合，不能先全库召回后只在展示时隐藏正文。当前摘要识别依赖前两页中明确的 Abstract/Introduction 边界；找不到可信边界就没有摘要候选，不偷偷回退全文。这也意味着特殊格式可能被漏识别。

**追问准备：** 这是材料范围控制，不是多用户权限系统。依据：[摘要边界](../paper_research/indexing.py#L10)、[检索过滤](../paper_research/retrieval.py#L71)、[范围测试](../tests/test_retrieval.py)。

### Q027【P1】PDF 多栏、公式、表格和扫描件怎么处理？

**参考回答：** 当前使用文字提取，复杂多栏顺序、公式和表格可能失真。没有文本的扫描件不能直接进入当前流程，需要先 OCR。回答应说明材料局限，表格数值和公式推导最好回到 PDF 核对。当前没有 OCR、布局识别或多模态表格解析，不能写成完整解决。

**追问准备：** 能提取出字符不代表阅读顺序一定正确。依据：[pypdf 文本提取说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)、[入库检查](../paper_research/indexing.py#L22)。

### Q028【P1】chunk_id 为什么由文件哈希、页码和偏移组成？

**参考回答：** 它把一个片段与具体 PDF 版本及提取区间关联，便于去重、缓存复用和回查。文件变化会改变哈希，切分变化会改变区间。但完整复现仍需固定提取库、清洗策略和模型版本，不能仅凭 chunk_id 就声称整个运行完全可复现。

**追问准备：** 检索结果还记录实际索引文件指纹，避免把不同索引的结果混在一起。依据：[indexing](../paper_research/indexing.py#L22)、[Retriever 初始化](../paper_research/retrieval.py#L46)。

### Q029【P1】新增、重复或更新论文时如何维护索引？

**参考回答：** 重复 PDF 按内容哈希复用已有文档；新增材料重建当前小索引，符合版本和文本条件的片段复用向量。建库成功后提交语料清单，索引用临时文件替换。现有流程不提供完整的在线删除、版本迁移或事务型多文件提交，规模增大需要重新设计。

**追问准备：** 索引与清单分别落盘，崩溃在两次替换之间仍可能不一致。依据：[ingest_job](../paper_research/api.py#L147)、[build_index](../paper_research/indexing.py#L82)。

### Q030【P0】中文问题检索英文论文如何实现？

**参考回答：** 向量分支依靠多语言编码器；Agent 规划阶段生成适合英文论文的语义/关键词查询，关键词分支还保留小型显式词汇扩展。词表不是通用翻译系统，改写也可能引入偏差，需要保留原问题做核验。当前手工评测含英文关键词辅助，这会影响方法公平性。

**追问准备：** 单独比较纯中文、自动改写、人工关键词三个设置，当前尚未完成此对照。依据：[expand_query](../paper_research/retrieval.py#L21)、[plan](../paper_research/workflow.py#L55)。
